## How this document is produced

Generated by `scripts/docs/render_er.py` from a live read of the migrated database. Re-run it after any migration and the document is current; nothing here is transcribed by hand except the descriptions, which live in `scripts/docs/descriptions.py`.

**It reads the database rather than the ORM, deliberately.** There is no single metadata object that covers this schema. Measured at this revision:

- `app/models/schema.py` alone registers **69** of 104 tables
- importing all eighteen model modules — `app/models/*.py` plus a `db_models.py` inside eight feature packages, all sharing the one `Base` in `app/db/session.py` — reaches **81**
- **23 tables have no SQLAlchemy model at all** and are reached only by raw SQL

So no import gives the whole schema, and a document built from one would quietly omit whatever its Base could not see. The database is the only complete answer, which is what this reads. The 23 model-less tables are listed in Appendix B.

## Appendix A — Environment drift

The three environments are not identical, and a document that did not say so would be misleading. Measured 3 October 2026:

| | Local (this document) | Supabase `founder-alley` | Production (AWS) |
| --- | --- | --- | --- |
| Alembic revision | `5b8e2f4a7c19` | `f8a3c26e4b91` | reported at head |
| Tables | 105 | 139 | not measured |
| Questions | 7,190 | 5,140 | not measured |

Three things worth knowing about that:

1. **Supabase sits on an orphan revision.** `f8a3c26e4b91` came from an unmerged branch (`claude/checkout-gst-billing`) and does not exist in the repository. Its real parent, `e5b2d47a91c3`, is 49 revisions behind head.
2. **Supabase has 39 tables this database does not** — mostly monthly partitions of `messages`, `analytics_events` and `audit_logs`, which are created by partition management rather than by a migration, plus `access_settings`, `beta_users` and `_perf_baseline`.
3. **Some reference data is seeded in Supabase but not here.** `agent_interpretations` holds 31 rows there and none in this database, so a figure of 0 in this document means unseeded locally, not deleted.
4. **The surrogate keys have diverged.** `questions`, `problems` and `root_causes` hold different id sets in the two databases, so no row can be copied between them by id. `question_code` and its equivalents are the only safe join keys across environments.
